# Flowchart Safe Class Styles Acceptance

## Delivered contract

- `classDef` and `class` are parsed from the Flowchart token stream, so class syntax uses the same CR/LF, semicolon, label, and comment boundaries as all other Flowchart statements.
- `classDef` accepts only named `fill`, `stroke`, and `color` values using three- or six-digit hexadecimal colors.
- `class` applies declared styles to declared nodes; repeated assignments cascade by field, with later values winning.
- Newline, semicolon, and tab-separated declarations use the accepted Flowchart statement boundary.
- The support preflight and Visual editor share the same statement scanner, which ignores `classDef` text inside pipe edge labels and recognizes class styles after multi-character arrows.
- Support validation matches parser class identifiers: Unicode letters and digits, underscores, numeric-leading names, and direction names are valid; lexer keywords are rejected.
- The SVG renderer validates serialized colors before assigning attributes.
- Visual editing is read-only for sources containing `classDef` or `class` until serialization can preserve them.
- Unterminated Flowchart node or edge labels fail before a partial AST is returned; support reports `flowchart.unterminatedLabel`, and Visual editing remains read-only.
- `click` remains an unsupported warning in loose mode; strict security and dangerous URL blocking are unchanged.

## Artifact size decision

The initial candidate reached 1,036,038 WASM bytes, 59,879 bytes (6.13%) above `0.1.8`, and triggered the required review. Rebuilding from clean output with the pinned release toolchain removed stale generated bytes without changing behavior.

The final byte counts compare the vendored `0.1.8` and pinned `0.1.9` release artifacts:

- WASM (`dist/xmermaid_wasm_bg.wasm`): 976,159 -> 994,083 bytes, an increase of 17,924 bytes (1.84%).
- ESM (`dist/xmermaid.esm.js`): 251,102 -> 261,549 bytes, an increase of 10,447 bytes (4.16%).
- **Rejected simplification:** remove parser-level class declarations or either the support-preflight and renderer validation. That would weaken the public syntax contract or move validation across a trust boundary.
- **Accepted rationale:** keep the bounded parser, preflight, and renderer checks because the clean pinned build brings both artifacts below the 5% review threshold. The remaining growth represents the delivered class-style contract and its defensive boundary checks.

## Deferred boundary

The visual editor intentionally does not preserve class definitions or assignments. It rejects visual source edits for diagrams containing them instead of silently deleting styling.
